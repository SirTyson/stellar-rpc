## Meta-Patterns

1. **Overhead too small to measure**: Most network-layer micro-optimizations save <400 ns against ms-scale `getTransactions` latency (DB reads + XDR decode + JSON serialize = 2–100+ ms). Anything saving <1% of request time is below the futurenet benchmark noise floor (±30% run-to-run variance at moderate RPS). Single atomics, map copies, debug-string allocations, and timer bookkeeping all fall into this category.

2. **Response-size asymmetry**: For `getTransactions`, the response body is orders of magnitude larger than the request body. Request-side parsing, encoding, and parameter handling are irrelevant to performance. Only response-side buffer copies, serialization passes, and streaming architecture are viable network-layer targets.

3. **Third-party code is a hard stop**: Any hypothesis whose primary target code lives in `github.com/creachadair/jrpc2` or another external dependency fails immediately. This is both a policy constraint (out-of-scope rule) and a practical one — the library's internal encoding is not a naive re-serialization.

4. **Correct code ≠ measurable improvement**: Timer deduplication (002-timers), timer cleanup (003-timers-live), and buffer pooling (004) all produced functionally correct implementations that passed all tests but could not beat ±30% RPS/latency benchmark variance on futurenet. The noise floor of the benchmark environment is the real acceptance threshold.

5. **Goroutine-accounting coupling**: The backlog queue limiter and duration limiters are intentionally coupled — the duration limiter's select loop must block until the downstream goroutine finishes because the backlog pending counter tracks real in-flight work. Any early-exit optimization on client cancellation would decouple accounting from reality and leak goroutines.

6. **Relocating work ≠ eliminating it**: Pre-encoding results as `json.RawMessage`, moving marshaling inside a timeout boundary, and changing the timeout window placement all move the same CPU work without reducing it. Only architectural changes that eliminate serialization passes or copies (e.g., streaming, zero-copy) can produce real gains.

7. **RPS-dependent regression risk**: The SummaryVec → HistogramVec + pre-bound observer change showed a +6.75% p50 improvement at 100 RPS but caused a 25–90% regression at 200 RPS. Metrics-wrapper changes can interact with GC pressure and benchmark noise in non-linear ways; a single-load-point validation is not sufficient for network-layer changes.

8. **Bridge micro-overheads require architectural context**: Small per-request bridge overheads (pending-response goroutine, request-side re-encoding, debug logger) cannot produce measurable gains in isolation. They are only worth addressing as part of a larger architectural change that eliminates the entire bridge round-trip.
